# 小说全流程编译命令

`nwh compile-novel` 从不可变原文一直执行到独立评估、认证、激活和可玩分支交付。默认继续已有编译进度；`--rebuild` 明确启动全量重编。完成标准遵循[小说编译流程与完整性验收规范](novel-compilation-protocol.zh-CN.md)。

```sh
# 首次编译：登记原文并执行全流程
nwh compile-novel fixtures/corpus/longzu_1.txt

# 已登记小说：默认续编
nwh compile-novel --source a28585b1cf867f3e3a16

# 首次监督任务即为全量重编；中断后保留同一次任务的恢复边界。
nwh compile-novel --source a28585b1cf867f3e3a16 --rebuild

# 只读查看各阶段、历史回执、实际缺口和独立评估状态
nwh compile-novel status --source a28585b1cf867f3e3a16

# 已有监督任务 DONE 后明确发起下一次重编：复制 status 返回的 supervision.stateHash
nwh compile-novel --source a28585b1cf867f3e3a16 --rebuild --loop-new-run <completed-state-hash>
```

各入口支持 `--root`、`--config`、`--source` 和 `--model`。全流程自动执行常规步骤，无需逐阶段确认；模型提案仍必须经过原有验证和提交屏障。`--branch` 可指定交付分支，已有分支固定的历史版本不能被覆盖。

完整命令默认启动持久化外层监督器：编译子进程退出后，先保存真实错误和状态，再调用本机 Codex 工程会话诊断并修复源码，交给独立只读会话复核，并执行 TypeScript 与固定回归测试。全部通过才以新进程继续同一编译，确保修复代码实际生效。已有阻塞先诊断，不原样重跑。工程会话默认 `gpt-5.6-sol / max`，可在首次启动时用 `--engineer-model` 指定；需要本机 Codex 登录及编译器源码、开发依赖。

监督状态和每次子进程日志保存在 `$NWH_HOME/workspaces/v1/<workspace>/compile-loops/<source>/`，`status` 的 `compilation[].supervision` 显示编译、修复、验证、停止或完成及诊断位置。工程修复保留已有工作区改动，不自动提交。每个确定性故障身份最多两个工程回合；通过预检不代表语义闭合，外层循环也不能清除领域预算或伪造提交。认证、激活及分支绑定仍由独立新进程核验。

工程会话按工作区和来源隔离，新注册表存于该来源目录的 `engineering-session/`；匹配来源的旧注册表原地沿用，不重建 UUID 或续期。重复调用已完成的监督任务只复核原成功回执、当前认证及分支绑定，不重新启动编译。复核失败会保留停止状态和原成功 worker；解决具体条件后只能续做复核。拒绝恢复请求时，原停止原因、时间戳和 `stateHash` 保持不变。

下一次完整重编必须显式使用 `--rebuild --loop-new-run <completed-state-hash>`。该哈希绑定唯一新代次：重复使用时继续或复核同一代次，不再新增任务。新代次保存在 `generations/<hash>/`，旧状态和全部回执保留，`supervision.directory` 指向当前代次。只有当前 `DONE` 可授权下一代；`BREAK`、在途子进程、过期哈希须先处理原停止条件，不能通过此参数补充领域额度。新代次的 READY 记录先落盘，再切换当前指针，最后启动 worker；指针写入失败可用同一哈希继续原待发布代次。

`--no-loop` 显式执行一次编译，供调试或已有外部监督器使用；单阶段命令和 `status` 保持原语义。迁移旧本地监督器可指定 `--loop-history <state.json> --loop-resolution <具体宿主审阅结论>`：仅接受同来源、同工作区且已停止的记录，保留旧计数、截止时间和失败历史；新的逐故障策略不重开任何领域尝试。原监督器需保持停止。外部授权、架构变更、未知写入、取消、工程模型不可用、复核拒绝或同故障重复无进展会保留明确停止状态，不通过换 ID、换模型或重开会话绕过。

宿主已解决一个明确停止条件后，可复制 `supervision.stateHash`，使用 `--loop-resume <hash> --loop-resolution <实际处理结果>` 重新检查原事故。该入口不增加工程或领域额度，已耗尽的同故障仍会停止。未再次指定的工作模型和编译选项沿用首次保存的策略；显式改变策略会停止要求核对。

如果工程回合已耗尽，宿主仍可提交已实际完成的源码修复：另加 `--loop-host-patch <hash>`，其 hash 绑定相对原事故基线的全部变更路径和当前文件哈希。监督器只进行独立复核与固定测试，不再启动一个工程回合；全部通过后才续编，旧计数保持不变。复核拒绝、测试失败或补丁变化仍会停止。具体计算方式和边界见[恢复协议](agent-tool-recovery.md)。

角色审计的一次性纠正如果因宿主误拒绝合法 `mode: detail` 读取而失败，命令会验证完整 trace、原授权及剩余额度。满足精确恢复条件时，宿主补齐只读内容，模型只使用原授权剩余的最后一次调用，通过原提案校验提交纠正；不重开任务、不覆盖失败记录，也不增加预算。

## 可单独执行的阶段

全流程与阶段命令使用相同实现。单独执行一个阶段只声明该阶段完成，不声明整部小说可用。

| 子命令 | 工作与交付 |
| --- | --- |
| `source [novel]` | 登记／校验不可变来源，准备当前结构计划 |
| `recover` | 新模型工作开始前恢复原始 finish 回执及已授权的上游修复 |
| `batches` | 继续结构发现、观察、身份与语义、可执行建模、跨片段边界批次 |
| `structure`、`observation`、`semantic`、`executable`、`boundary` | 只执行所选批次阶段；前序依赖仍须完成 |
| `converge` | 验证并提交待处理提案，保留被拒草稿和未解决义务 |
| `opening` | 建立有来源证据的初始世界 |
| `roles` | 独立全文角色复核，登记主要角色能力要求 |
| `repair` | 恢复已授权的上游修复，执行图关系和世界语义修复 |
| `requirements` | 重验已登记要求、关键延后项及全局闭合条件 |
| `closure` | 在编译锁内重新校验当前计划的原始 finish 回执、执行义务、来源记账、身份／角色交接和全局编译维度；保存逐维度结果 |
| `archive` | 归档不可变候选；不改变 active 指针，不授予认证 |
| `evaluation-plan` | 生成／复用／导入并冻结独立 gold、字段支持复核和逐主要角色场景规格 |
| `evaluate` | 执行独立真实 Pi 实验，复用相同候选和规格下已完成的实验 |
| `certify` | 检查全部认证门禁，归档带认证的候选，尚不激活 |
| `activate` | 验证候选仍对应当前编译输入，再切换 active 指针 |
| `branch` | 创建或复用固定到当前认证版本的可玩分支 |
| `status` | 只读快照；不调用模型、不迁移、不重验、不激活 |
| `plan` | 只读生成全部后续阶段、依赖任务、原始引用和恢复条件；不新增授权、不启动监督器 |

例如修正角色复核后继续后续流程：

```sh
nwh compile-novel roles --source <source-id>
nwh compile-novel --source <source-id>
```

默认续编会重新核对每个阶段的当前证据：复用批次检查点、原 finish 回执、已完成角色审阅、同候选的冻结评估规格及有效实验结果。历史调度记录中的 `completed` 不能替代当前版本的认证。

### 批次完成后的统一交接

```sh
nwh compile-novel plan --source <source-id>
nwh compile-novel closure --source <source-id>
```

`plan` 的 `sources[].handoff.tasks` 保留全部阶段和已发现的身份消费者、来源审计、上游修复任务。每项包含稳定 `id`、`dependsOn`、原始 `refs`、结构化 `command` 和 `resumeCondition`。`recorded` 只表示历史调度回执；`available` 表示存在原有阶段入口，实际执行仍需通过该入口的当前权限与依赖验证。`inspect-only` 不可作为模型续跑或写入授权。尚未完成语义诊断的范围仍由对应阶段负责，计划不宣称已发现原文中的全部遗漏。

结构化命令携带被检查工作区的绝对 `--root`，可从其他目录执行而不切换修复范围。上游计划处于 `evaluated` 不等于要求已满足：未满足或未知结果继续显示为阻塞任务。闭合阶段还会以当前候选重验已评估计划，旧评估与当前输入不符或无法验证时保留阻塞；不会自动替换原评估或续期修复授权。

已收敛的上游修复交给 `requirements` 重验，不再重新 staging。已授权且保留原 finish 审阅的修复继续使用 `recover`。负面的来源审计修复、未完成的身份消费者审查和无法读取的依赖记录，会在 `roles` 的新模型调用前停止，并给出原任务入口。未审分片、额外修复和重验需求不会因一个独立审查返回 supported 而消失。该交接不创建新的身份续跑许可；缺证据、缺受支持的消费者修复类型或已耗尽的授权仍保留明确阻塞。

迁移已退休的角色计划保留在历史中，`roleReviewWork[].current` 区分当前分母；不会将两代审查数量相加。`status` 的 `compilation[].handoff` 使用同一交接实现。

角色依赖或闭合检查的领域阻塞会随阶段回执保存结构化 `recovery`。监督器转交同来源 `plan` 中的原任务，不为同一语义缺口启动工程回合或原样重复编译；真实工程异常仍沿用既有修复协议。只读检查失败标为 `host-state`，不能当作语义缺证据或成功。

CLI/TUI/Web 不再合成单角色 `alive=true` 开局。调用失败时保留原错误、会话与草稿；只有正常结束但未产生可用开局，才报告 `phase:opening` 语义阻塞。工程异常和提供方异常不会被改写为原文缺口。

完整 CLI 和 TUI 交付链在 `requirements` 后、`archive` 前执行 `closure`。这个阶段调用现有审计与要求账本，验证当前计划每个原 finish 回执，并分别检查来源、批次、执行义务、角色来源审查、上游交接、结构、证据、记账、决议、语义和已登记要求。`unknown` 不算通过，关键延后保留全部单元引用。结果保存在原编译运行的 `closure` 字段，失败也落盘；它是带来源／编译指纹／审计哈希的调度快照，不另建语义真值账本。修订后必须重新运行，不能凭旧快照跳过检查。

该闭合检查不代替后续独立支持规格、真实 Pi 实验和认证。`archive` 单阶段命令仍可保存未认证候选，active 指针保持原状；完整交付须继续通过评估、认证和激活。

### 短 demo 与回归

```sh
pnpm demo:compilation-completion
```

这个可重复的确定性 demo 使用临时小说和隔离工作区，不调用付费模型。它验证：检查点 100%／零执行义务仍不能跳过真实回执与缺口；闭合失败持久保存；状态与计划读取不写状态；未认证候选可归档但不激活；部分身份分母、退休角色计划和已消费的负面审计被正确交接；已收敛修复转入重验。demo 同时是普通测试集的一部分。它证明流程行为，不证明《龙族》语义内容已补齐或真实多轮体验已通过。

### 角色审计恢复

角色复核阶段现在由同一命令调度有界修复，无需临时脚本逐页接力：先完成来源记录、候选判定及其独立核验，再收齐来源审查中的全部问题。未受支持的候选判定复用既有单次修订机制；来源审查中的遗留问题各允许一次修复提案和一次独立验证。修复可检索同一小说的非相邻章节，但不能删除原问题、遗漏角色要求或覆盖原审查结果。修复与验证共享继承的累计用量，独立验证通过后写入要求账本和最终审阅证据；仍缺证据或验证为否时保留阻塞。

来源审查因已确认的 Codex 用量限制中断后，额度恢复时再次执行同一条 `compile-novel --source …` 即可尝试续跑。宿主先核对原 trace、完整工具结果、原任务和依赖，恢复原草稿并重新读取证据，只消耗原来剩余的会话和无进展额度。未完成写入、工具失败、预算耗尽、会话耗尽或无法验证的旧任务不适用自动恢复，仍按具体诊断停止。`status` 中的 `roleReviewWork[].sourceAuditRepairs` 显示修复提案和独立验证状态；审查和修复成功仍不等于全书认证通过。

## 独立规格与评估

没有适用规格时，`evaluation-plan` 使用独立 Pi 会话读取整部不可变原文、分项提交 gold 和场景草稿、复核可执行字段的来源支持。它没有修改世界真值的工具。草稿、原文阅读页偏移、真实审阅 trace ID、纠正次数和停止条件均持久化。完成冻结前检查全文阅读范围、规格引用、主要角色分母及入口切面。

也可提供人工或外部独立审阅后的 JSON，格式为 `novelEvaluationPlanInputSchema`：

```sh
nwh compile-novel --source <source-id> --evaluation-plan reviews/novel-evaluation.json
nwh compile-novel evaluation-plan --source <source-id> --evaluation-plan reviews/novel-evaluation.json
nwh compile-novel evaluate --source <source-id> --plan-hash <frozen-plan-hash>
```

完整通过仍要求现有 `novel-play-v1` 策略：独立语义指标、关键检查、机制支持、全部主要角色的入口探针，以及每个主要角色三次独立真实 Pi 实验；每次须达到 50 个实质提交或验证的合法终止，并通过任务、知识隔离和重放要求。单元测试和确定性测试夹具不能取得真实 Pi 认证。

候选变化后旧评估失效，重新冻结并执行相应评估。确定性预检失败时先返回具体缺口；失败或写入状态不确定的真实实验保留原 ID、trace 与分支，要求按诊断恢复，不通过生成新实验或更换规格清掉失败。

## 重编、阻塞与恢复

全量重编先检查原有未解决义务、待恢复 finish、待处理提案及其他修复任务；存在这些状态时保留原任务并明确停止。可归档的当前候选先作为不可变基底保留，然后失效本来源的当前编译产物和批次完成标记。历史失败、要求账本、归档版本、active 与已有分支历史保留。初始化完成后，中断恢复不再清空已完成的新批次。

失败信息给出实际阶段、原始诊断和可单独执行的阶段命令。已有授权的上游修复可用 `--upstream-plan <hash>` 继续；需要原始宿主 finish 审阅时配合 `--upstream-finish <path>`。本命令不把诊断计划自动变成写权限，也不绕过宿主审查、来源不足、未映射能力或持久化熔断。

只有最后的认证、激活和分支交付全部通过，才输出 `Novel compilation complete`。出现阻塞会以非零状态退出；72/72 批次、零执行义务或候选归档均不能触发该完成声明。

旧的 `compile-source`、`prepare-all`、`rebuild`、`reparse`、`repair-existing`、`requirements` 和 `prepared-cache` 入口保留兼容。其中 `prepare-all --candidate-only` 仍只负责候选准备；完整交付请使用 `compile-novel`。

Pi TUI 的 `/prepare-all` 在候选准备后复用 `compile-novel` 的角色复核、修复、要求重验、全局闭合、归档、独立评估规格、评估、认证和激活阶段。通过这些门禁后才询问是否创建可玩分支；任何门禁失败均保留诊断，不声明准备完成。
