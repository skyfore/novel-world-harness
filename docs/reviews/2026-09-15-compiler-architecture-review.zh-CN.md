## 3. 仍未解决的关键问题

### 3.1 高优先级：个案补修没有沉淀为通用依赖修复流程

源码中没有检出所审查小说名称或主要角色名硬编码。但大量语义决策存在于 `run-records/2026-09-11-codex-compile-loop/review-*.ts`：

- `review-control-room-entity-and-link.ts:23` 起，脚本给出特定地点 ID、名称、提及 ID、固定原文行号和身份判断。
- `review-cousin-bedroom-entry-checkpoint.ts:36` 起，脚本构造具体房间、角色入场叙述、观察和 location delta，再通过正常 proposal/finish/converge 提交。

这些脚本通常仍保留原文核验、锁、回执和发布门槛，不能简单指控它们绕过验证。问题在于：**完成领域解释工作的主体成为一次性宿主脚本；新小说不能复用这些解释能力。**

调用链进一步说明了缺口：`prepare-all.ts:620` 的常规 reconciliation 禁用 annotation、entity-resolution、event-resolution 和 accounting 写工具；`knowledge-repair.ts` 单独开放 claim/proposition/attribution 依赖，却仍不能处理缺失实体、错误引语范围等前置依赖。设计选择本身保证了权限边界，但当前缺少把这些阻塞转换为受限上游修复任务的统一入口。

应从案例提取通用缺口类型，例如：身份提及缺少决议、话语范围不完整、前事件角色状态缺失、获知路径缺失、机制效果无法表示。规划器按声明的依赖边生成受限修复计划，不需要按每个人名、地点名新增脚本；真正改变本体含义或权限范围时，再交给宿主设计审查。

### 3.2 P1：引语内容验证存在可复现的字段覆盖漏洞

位置：`src/compiler/attribution-trace.ts:96–106`。

检查器把 `/object` 及所有子指针汇为一组，然后使用 `content.some(...)`。因此，一个对象类型字段的证据落在引语内，就足以掩盖实际内容字段的证据落在引语外。

函数级反例：

1. 引语范围 `[0,10)`；命题 `/object/value` 证据范围 `[20,30)`：返回内容越界错误。
2. 保留上述错误内容，再加入 `/object/kind` 的证据 `[0,5)`：返回空错误列表。

这违反该函数“所归属内容必须由引用话语支持”的目的。新增测试只覆盖单条 assertion 的多 anchor 情况，没有覆盖不同对象子字段之间的替代。

不能简单改成所有 assertions 都必须在每段话中：同一命题可以被多个人在不同场景重复表达，全局命题证据不应被强制限定到每一次话语内。

需要分离两件事：

- 命题作为可复用的语义内容；
- 本次话语表达了哪些命题内容，以及本次归属边的证据。

应验证本次归属边对语义字段的支持覆盖；`/object/kind` 等结构字段不能替代 `/object/value`、实体或嵌套内容。没有足够精确证据时应显式返回未证实状态，而非把兼容旧数据的空结果解释为证实。

### 3.3 P1：逐目标报告遗漏“部分修复”的持久义务

位置：`src/compiler/reconciliation-review.ts:39–46`、`:23–24`；`src/compiler/reconciliation-review-ledger.ts:26`。

当前目标粒度是 `character:<id>` / `event:<id>`。只要角色有任意 character-goal 或 character-model 提案，就必须报告 `proposed`；剩余缺口只能写进自由文本 summary。宿主复核门槛则只记录 `disposition !== proposed` 的目标。

函数级反例：同一角色需要“目标”和“人物本体迁移”，仅提交目标，summary 写明“迁移仍为 capability gap”。校验返回无错误；后续 audit 可以同时输出：

```json
{"status":"unresolved","hostReviewRequired":false}
```

这不是已证明的发布绕过：当前全局 audit 仍可能阻止发布。但“每项未完成能力均有不可遗忘的结构化义务”并未实现；自由文本中的剩余缺口没有与原目标绑定的强制结算路径。

建议把目标拆成带 requirement ID 的检查项，例如 actor 的 ontology、development、opening-driver 三项分别记录 proposed/satisfied/unsupported/capability-gap。完成由各自后置条件决定，允许部分成功；一个提案不能替整个角色消除其他要求。

### 3.4 中优先级：最新 direct-observation 修复只验证标签组合

位置：`src/compiler/knowledge-repair.ts:82`；`test/knowledge-repair.test.ts:13–24`；`src/compiler/attribution-trace.ts:181` 起。

新增检查要求 acquisitionMode=observed 且没有 attributionId/sourceActorId。测试明确显示：保留同一 claim/proposition，移除两个来源字段并改成 observed 后，作用域检查通过。

这能阻止“明示为转述”的操作进入直观观察补修，却不能单独证明该信息确实来自此时此地的感知。一般 evidence/schema 校验仍会执行，因此不能据此断言所有此类输入都可提交；但新增三行没有建立事件、感知来源、观察者与获知时间之间的确定性绑定。

需要让知识获知边携带本次 acquisition 的来源：当前事件/场景 cut、感知或话语证据、观察者/听者、渠道及可达性。原文可信度、命题真假、角色相信程度、获知时间应分开建模。否则“将一个晚期报告改标签为早期观察”的问题仍依赖模型自律和宿主阅读。

### 3.5 中优先级：开局驱动选择修复了错人问题，尚非能力规划

位置：`src/compiler/opening-driver.ts:2–8`。

物理在场焦点角色优先于全书参与次数，正确修复了本次已知错配。但无焦点时按 ID 字典序选第一个物理角色；没有物理角色时又退回全书参与次数。

这只能生成候选修复对象，不能证明该角色有原文支持的主动行动，也不能处理“焦点被困/昏迷，真正驱动力来自另一个角色、机构或环境过程”的一般情况。当前检查仍有防止错误激活的价值，不应把该 helper 当成自主世界能力已成立的证明。

后续应从开场已成立条件及可执行计划/过程发现驱动候选，再验证至少一个候选的动作前提和非空结果；角色出现频率不作为能力证据。

### 3.6 中优先级：独立验收尚未接入统一的能力完成契约

`scene-capabilities.ts` 是本轮最值得保留的架构增量之一：预期来自独立来源审查，执行确定性状态/知识/规范探针，并明确区分 verified、blocked、unknown、unsupported。

但其生产调用目前在 `review-scenes` 命令中；常规 prepare-all 的逐目标完成依据仍是全局 audit。人物成长率、参与标注率等阈值可以帮助定位问题，不能证明任一关键能力已经成立。源码也已明确把目标消失称为 `no-current-audit-finding`，并未声称它是 certification；这个边界应继续保留。

已有可执行世界和长时间分支测试验证了一部分历史重放、状态隔离和反事实行为；不能说仓库没有运行时验证。缺少的是把此次暴露的身份、获知、角色切入和机制表示缺口，系统性接入这些运行时验收。

## 4. 最终是否真实解决

已提交的 `status-after.json` 时间为 **2026-09-13 23:20:17 UTC**，不是本次对实时生产状态的查询。与之对应的 `state.json` 记录：

- 第 183 次尝试，`needs-review`，停在 repair。
- 来源核算：0 unaccounted，但仍有 600 blocking units。
- 身份/事件决议维度：197 missing、12 ambiguous/unresolved mentions。
- exact evidence 仍为 unknown。

由此可以支持三项判断：

1. 恢复机制有效推动了多轮工作，也有效保留并暴露了未完成状态。
2. 不能把 71/71 批次、补修回执、无 pending、测试全绿等价为完整世界已可用。
3. 大量个案补修后仍有成批同类型缺口，说明应优先提炼遗漏发现与受限依赖修复能力；继续逐条宿主填写不是通用问题闭环的证据。

无法仅凭此快照区分所有缺口分别来自原模型能力、过窄修复权限、旧工件迁移、原文歧义还是本体不足。应把这些原因结构化分类后再安排工作，不能把它们一概归为“模型不听话”，也不能全部算作“世界模型缺字段”。

## 5. 建议的架构工作顺序和验收

### 第一阶段：修复两个已复现的协议/验证漏洞

- 引语归属按内容字段和本次表达边校验；覆盖多子字段、复用同一命题、多引语、嵌套命题、旧证据不足的反例。
- 逐目标报告升级为逐能力要求的义务；覆盖部分成功、迁移成功但驱动失败、跨重启、后续回归、全局比例改善但单项仍缺失的情形。
- 使用小型独立文本 fixture，通过真实 proposal → finish → converge 验证；补充坏输入没有改变 canonical artifact 的断言。

### 第二阶段：统一受限依赖修复

建议的契约要素，不是本次已经实现的类型：

```text
CapabilityGap
  requirementId / diagnosticCode / source scope / branch or canonical cut
  affected artifact IDs / required dependency kinds / evidence references

RepairPlan
  predecessor receipt / baseline hashes / writable fields
  allowed dependency edges / immutable dependencies / postconditions

RepairResult
  per-requirement outcome / committed revision references
  unresolved obligations / capability evaluation references
```

模型仍只能调用窄提案工具；宿主执行作用域、证据、版本前置条件和后置条件验证。不要用开放文件写工具取代这一层。错误原因应来自结构化诊断，不依赖解析自然语言或按小说对象不断编写特例。

### 第三阶段：从案例抽取模型能力，接入运行时

| 抽象能力 | 最小验收场景 |
| --- | --- |
| 稳定身份与语境指代 | 同名不同人、同人不同称呼、群体与个体、远程呈现与物理在场；不能为链接覆盖率强行合并 |
| 话语与知识来源 | 重复表达同一命题、相邻话语内容不同、误传、翻译、晚期报告；角色知识必须按获知边及 cut 投影 |
| 角色切入 | 入场点是未解决的 pre-event cut；不能把事件结果、晚期目标或后获知识放进开局 |
| 可执行变化与本体扩展 | 状态条件、设备生命周期、短暂失能等先定义语义与 reducer，不把 launched 等标签塞进数值 condition |
| 自主推进和反事实 | 焦点角色无动作时仍有合法驱动；玩家破坏 canon 前提后，未来失效或改道，而非强制回归原剧情 |
| 增量修订 | 修复某依赖后重验受影响图；保留未授权字段及历史；能够说明哪些既有能力仍然成立 |

每项能力都应同时有：正例、反例、缺证据时的 unknown/blocked 路径，以及必要的分支重放验证。再用第二个独立构造的场景检查抽象是否仅适配原案例。

### 第四阶段：改善交付和证据组织

- 架构/源码与通用验收按实际增量提交，个案运行记录保存在仓库外。
- 已提交的历史运行材料通过 Git 历史追溯；仓库正文只保留经验提炼，不保存中间状态或大体量快照。
- 对每次经验提炼记录：原案例暴露了什么、归属协议还是领域模型、抽象契约是什么、哪些反例可推翻“已修复”。
- 本次不建议继续补齐该书，也不建议在能力契约尚未验收前把范围扩大到更多整本小说。
