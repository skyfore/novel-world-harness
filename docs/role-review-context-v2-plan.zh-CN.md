# 角色复核上下文与核验能力统一方案 v2

日期：2026-09-29。状态：核心门禁与一次有界补证已实施；分层语义导航、自动差异修复和真实 Pi 质量验收尚未完成。设计要求与当前实现边界见文末。

本方案修订 `role-review-context-design.zh-CN.md` 的执行策略。保留已实现的隔离 Pi 工作、原文权威、持久进度、原 batch 身份、提案 journal、出站请求检查和全局 finish；替换仅靠固定小块、可选检索及空 unresolved 列表的核验方式。

首先应用于独立角色复核：主要角色分母、重要性、发展预期与补漏。其他小说编译阶段可复用基础机制，但必须分别定义证据要求，不能直接把本阶段的上下文策略推广为全部编译策略。小说语义工作由 Pi 执行；当前 Codex 负责源码、协议与工程测试。

## 1. 设计决策

目标是保持跨章节理解、可核验判断和可恢复执行，在此基础上减少冗余输入。不能以最短上下文、最少调用、草稿最多或批次全绿代替质量目标。

统一采用：

**来源覆盖 → 本轮全局导航 → 问题定义与证据计划 → 动态证据包 → 判断提案 → 反证审计 → 差异修复 → 原有全局 finish。**

这些是明确的阶段与产物，不要求由一个会话全部完成。跨会话保留结构化审阅状态，不保留无限增长的 transcript。

必须分别证明：

1. 阅读范围覆盖：哪些原文范围已经审阅，哪些只是取回或仍未处理。
2. 问题闭合：应回答的问题是否逐项处理，是否仍有影响判断的证据缺口。
3. 证据支持：具体结论是否得到原文支持，是否处理已知反证。
4. 全局一致：角色身份、重要性和发展结论是否与其他片段矛盾。
5. 协议合法：来源、版本、权限、预算、历史与提交回执是否一致。

代码可确定性检查覆盖、引用、版本和明确的闭合结构；语义支持与文学重要性由 Pi 作出判断并接受审计。访问回执不能证明模型理解充分，语义审计也不是形式化正确性证明。

## 2. 本轮源码复核发现与修订要求

| 当前问题 | v2 必须改变的行为 |
| --- | --- |
| `openQuestions` 与审计 `unresolved` 没有逐项对应 | 每个问题有稳定 ID、影响对象和明确处置，不能通过新交空列表消失 |
| 补漏初始包只有全体候选名字／ID | 审计包必须带当前被审判断与 revision，读取和判定覆盖成为门禁 |
| 审计只检查引用 ID 属于原文 | 审计同样要求 decisive evidence 已交付／完整回读，且报告语义支持或反驳关系 |
| 单角色初始包主要是候选元数据 | 宿主依据本轮索引装配相关背景、支持证据、已知反证及未解问题；Pi 再按需扩展 |
| 已成功旧草稿自动跳过新核验 | 保留其历史，但新增要求必须由专门复核工作覆盖，不能直接升级认证 |
| 48,000 字节／12 次调用一刀切 | 保留安全门禁，增加有界的任务拆分与证据扩展协议；额度不是语义充分性标准 |

## 3. 三层上下文与一个持久问题清单

### 3.1 全局导航：知道全书有哪些相关关系

每轮独立审阅维护自己的 `ReviewAtlas`：

- 章节／场景导航与来源指针。
- 人物和别名假设、未解指代、身份歧义；不能自行写入 canonical identity。
- 重大行动、关系变化、叙事转折、角色发展线索及已发现反证。
- 叙述顺序、可能的故事时间，以及梦境、回忆、引述、假设等归属。
- 仍有争议的判断与对应问题 ID。

它是有修订号的审阅提案，不是世界真相，也不是唯一证据。每个语义导航项至少带来源引用、支持边界和不确定性。

导航采用分层索引：全书根目录保持简短，章节卡、关系卡、事件卡按任务展开。不能把所有卡片永久塞进每个请求；当前角色收到的是相关关系与转折视图，同时能够查看其他章节目录，避免只能沿既有过滤结果行动。

后文改变早期假设时，保存修订及依赖关系。受影响的工作包和判断标为 stale，只重新审查相关部分；既不无条件接受早期摘要，也不每次重跑全书。

### 3.2 当前证据包：足以回答当前明确问题

`EvidencePacket` 不以人物名字匹配次数为核心，而以当前判断所需证据类别组织：

| 判断 | 必需证据类别 |
| --- | --- |
| 人物重要性 | 因果行动、关系作用、视角地位、后果；低频关键行动与晚出场线索 |
| 持久发展 | 前状态、触发／经历、后状态与后续行为；时间关系；反证 |
| 稳定性 | 跨已审来源范围的连续性、已发现变化线索的处置；不能从未搜到变化推导稳定 |
| 身份映射 | 名字／别名／指代证据、歧义上下文、不同身份的反例 |
| 遗漏角色 | 来源独立发现项与冻结候选清单的逐项映射／区别解释 |

包内区分 `required`、`counterevidence`、`background` 和 `unresolved`。所知反证、未解身份和影响当前结论的问题不能被普通相关性排序挤掉。

证据先按规范来源范围去重，再在不破坏说话者、叙述层次、时间关系的前提下装配。对话归属不明时展开完整交换；发展前后对照必须同时保留决定性原文；长场景可拆成子问题，但最终判断必须再次获得关键原文与仍存疑点。

证据充分性要求本身是可修订的模型提案和阶段规则，不是宿主凭字符串命中决定的语义事实。

### 3.3 原文扩展：允许发现当前包之外的证据

Pi 可以使用本地词法搜索、来源导航、同轮关系／身份假设和审阅发现项定位原文。搜索结果只定位，不证明未命中对象不存在。

上下文不足时返回 `EvidenceNeed`，明确：当前问题、缺什么、为什么会改变结论、已有查找结果、期望来源范围或发现工具。宿主核验 scope 和历史后安排补证。

允许导航失误被纠正：Pi 可请求查看尚未展开的目录、不同章节或原有筛选之外的原文；但不能越过来源、review 独立性或 runtime 知识边界。

### 3.4 问题清单：上下文可以换，责任不能丢

开放问题进入已有 requirement/repair ledger 的角色审阅扩展记录，work store 只保存执行状态及引用，不能维护一个可独立清零的平行语义账本。

问题至少包含：`questionId`、来源依据、影响的角色／claim、严重性、依赖、当前状态和处置记录。状态为 open、evidence-needed、resolved、superseded-with-reason、blocked；unknown 是结论状态，不能自动把问题置为 resolved。

每个 audit 必须覆盖它负责的 expectedQuestionIds。少交一个、漏看一个 revision 或没有合法处置都不能完成。后续增加问题会使受影响的 audit 失效。非关键延期须服从现有协议，不能为了 finish 临时降低严重性。

## 4. 执行阶段与交接

### A. 固定范围与连续来源审阅

冻结 source hash、结构、候选 subjectHash、review revision、parent batch 和本轮计划。结构 core 保证原文覆盖，context halo 只为理解服务，不重复计数。

结构块不宣称是完整场景。Pi 可要求邻段、完整对话或其他上下文；宿主根据结构扩展可确定边界，语义场景边界由 Pi 提案并保留证据。发现问题即入账。

先做不依赖角色重要性标签的全书发现，保留未在上游候选中的人物。对每个 core 记录 delivered、reviewed 或 blocked，reviewed 需有效提案而非单次页面访问。

### B. 建立与修订全局导航

由同轮 Pi 将分段发现整合成导航卡和关系／时间假设；任务按问题与相关卡组织，不能做一次吞下全部笔记的总摘要。

整合结果允许冲突共存，并将冲突指向问题账本。导航根目录可由宿主从受检卡片生成；宿主不得擅自决定人物同一性或因果关系。

### C. 形成角色问题清单与证据计划

冻结候选清单与本轮发现项映射后，每个候选创建重要性、发展预期和相关身份问题。为每个问题记录需要的证据类别、现有证据、缺口与反证检索责任。

高风险判断包括关键角色、跨章身份合并、持久发展、与旧结论冲突、来源发现但未映射的人物。根据可见复杂度安排相应工作包，不能只按角色出现次数决定上下文大小。

### D. 局部判断与补证循环

Pi 收到相关导航、当前问题、证据包和所有已知阻塞项，产出三者之一：

- `propose_judgment`：结论、精确证据及证据关系、反证处置、适用范围和依赖 revisions。
- `request_evidence`：具体缺口与补证请求。
- `report_indeterminate`：已审范围、剩余歧义及影响；不是成功认证。

若需要细分，宿主产生绑定 parent work 的子任务，保留总预算和历史。最后的整合工作必须携带各子任务的结论、冲突和决定性原文，不能只凭子任务摘要进行裁决。

### E. 分层审计

先审具体 claim，再审角色整体，最后做全书遗漏／跨角色一致性检查。

每个审计工作包必须含被审 claim 的全文、revision/hash、责任问题清单、相关原文和已知反证。不可只给名字，期待模型自行想起读取判断。

对每个 claim 返回 supported、contradicted 或 insufficient，并说明与原文的关系；对每个问题返回带证据的处置。允许提出新问题并回到 D。正确性不由“审计调用成功”代表。

全局检查结合来源覆盖和发现映射：检查未映射人物、晚出场与低频因果角色、跨章节身份及发展冲突。抽样只能作为质量监测，不替代必需范围覆盖或必需问题的审计。

### F. 差异修复与提交

审计变化产生既有 repair ledger 中的有界任务。只重跑受影响 claim，保留前版本及失败次数；合法修订需有新证据、明确缺陷或新的审计问题，不能任意重复。

提交门禁检查来源覆盖、候选分母、发现项映射、问题处置、claim audit、依赖 revisions、失败义务和 finish 回执。仍保持局部工作、独立 review、全书闭合、认证和激活相互独立。

## 5. 上下文装配算法与动态大小策略

每次组包按以下次序执行：

1. 固定本次问题、来源身份、当前 revisions 和工具权限。
2. 注入简短的全局导航及与本次问题直接相关的关系、转折和疑点。
3. 装入必需原文与已知反证，保证叙述归属、时间和局部场景足够完整。
4. 添加确有用途的补充背景；去重已包含的来源范围和重复协议字段。
5. 输出 manifest：includedRefs、omittedRefs、omitReason、requiredButMissing、questionIds、claim revisions、packet hash。
6. 校验最终 provider payload。必需材料装不下时，进入补证子任务、显式扩展或 blocked，禁止静默删减。

大小使用三层控制，不能以硬限制代替证据判断：

- 工作类型的目标区间：例如初始实验普通角色 16k–32k token，分段发现 12k–24k；须用真实 tokenizer 或明确标注的不确定估算校准。
- 有证据理由的难例扩展：例如 32k–64k 的跨章比较，仅为实验候选值；还必须满足真实模型窗口、输出预留、请求字节上限和原 loop 预算。
- 请求前硬 admission：超限绝不发送；不清零预算。若无法可靠估算 token，保留保守字节后备，状态应为需要重组任务，而非解释为证据已充分。

当前 48,000 字节限制先作为保护机制保留，待校准并完成扩展协议后替换，不能直接放大到 64k token 等价物。当前每工作 12 次调用同理：到达软规划边界时可提交工作交接；触及硬限制后停止，由宿主依据持久缺口安排合法的新工作，不能让模型换 work ID 获得新额度。

较大上下文适用于明确的跨章综合问题；小上下文适用于局部证据核对。无论大小，都记录何种证据使任务需要该规模。

## 6. 数据合同（草案）

```ts
type ReviewQuestion = {
  id: string;
  reviewId: string;
  claimIds: string[];
  sourceRefs: string[];
  impact: 'critical' | 'noncritical';
  status: 'open' | 'evidence-needed' | 'resolved' | 'superseded' | 'blocked';
  resolutionRef?: string;
};
type EvidenceNeed = {
  questionId: string;
  missing: string;
  decisionImpact: string;
  searchedRefs: string[];
  requestedScope: { sourceHash: string; chapterRefs?: string[]; evidenceRefs?: string[] };
};
type JudgmentAudit = {
  claimId: string;
  claimRevision: string;
  packetHash: string;
  requiredQuestionIds: string[];
  evidenceRefs: string[];
  verdict: 'supported' | 'contradicted' | 'insufficient';
  rationale: string;
  questionDispositions: Array<{ questionId: string; dispositionRef: string }>;
};
```

所有引用由宿主发现工具发放；语义 severity、alias、时间关系与证据支持仍属于提案，经相应校验后进入审阅记录。短引用可减少协议开销，但必须绑定来源、packet 与规范 unit ID；不是第一期修复的前提。

## 7. 核验门禁与可证明边界

必须由代码检查：

- 每个必需 source core 有审阅回执，边界扩展没有重复冒充覆盖。
- 每个候选及来源发现项都有合法处理；不能通过不提案减少分母。
- 每个 expectedQuestionId 有合法处置或阻塞；不能用空 unresolved 清除旧问题。
- audit 覆盖精确的 claim revisions；读取回执绑定本工作、原文范围与 packet。
- 角色和审计引用的决定性原文均已完整交付；缺失邻文需求尚未解决时不通过。
- stable/changes/unknown 各自的证据合同得到显式回答，已知反证得到处置。
- 依赖更新后旧 audit 不再有效；无法确定是否受影响时标 stale，不默认为有效。
- 未决关键问题、未恢复失败、耗尽、scope 变化和不确定写入阻止全局 finish。

代码不能证明文学解释一定正确，也不能证明模型没有漏掉未知反证。通过独立第二轮、针对性反证审计和语义评测降低风险，报告剩余不确定性，不能把结构检查包装成语义认证。

## 8. 独立性与旧草稿接续

两轮可共享原文、结构布局及不含模型判断的确定性索引。不能共享语义导航、别名推断、角色重要性、发展结论、审计 verdict 或基于前轮判断的证据排序。原候选清单可作冻结分母，但来源发现阶段不得只围绕候选名字搜索。

两轮结果比较属于后续 reconciliation，不能反过来污染独立初判。

对现有 28 条草稿：保留原提案和历史；为缺少新版合同的条目创建 `legacy-verification` 工作，读取其判断、原引用及本轮新增反证。新门禁通过后记录 adoption/verification receipt；有矛盾则通过正式修订流程处理。绝不直接跳过，也不全部推倒重做。

旧的开放问题字符串迁移为稳定 ID，保存原输入与映射。新版本对不具备问题处置和 claim audit 的旧 v3 证据标记为 legacy，不自动升级认证。版本判定与 cache/finish 同步测试。

## 9. 调度、恢复与观测

工作层级为 source → independent review → parent batch → work/child work → invocation。进度、失败次数和累计预算归属于原 review/loop；更换会话、细分工作、调整 packet 都不重置它们。

持久记录计划、atlas revision、问题、证据需求、claim、audit、尝试与回执。只有工具调用而没有有效新证据、问题处置或产物变化不算进展。重复相同补证请求、重复相同诊断或多次无进展必须停止。

恢复时重建当前 packet，不重放整个 transcript；若已完成结果的落盘状态不确定，先检查原记录，不重复派模型。provider quota 与执行 deadline 单独停机，不自动切账号或模型绕过。

状态同时报告来源覆盖、开放／关键问题、有效 claim audits、旧草稿待复核数、上下文大小、缓存与非缓存用量、重复原文比例和停机原因，不能只报 staged 候选数量。

## 10. 验收与实施顺序

### 第一批：先封住可能错误通过的路径

问题 ID 与逐项处置、审计强制包含 claim、审计原文回读、旧草稿 verification、依赖失效；保留当前有界上下文。测试必须证明“遗漏处置／未读取判断／只知道 ID”无法变成全绿。

### 第二批：补齐全局理解与证据组织

ReviewAtlas、候选与发现项映射、关系／时间疑点索引、支持与反证 evidence packet、精确邻段／场景扩展。先用单 Pi worker，避免同时引入并行协调变量。

### 第三批：补证与有界修复循环

EvidenceNeed、子任务与重新整合、动态上下文 admission、问题驱动修订和 stale propagation。预算共享与禁止无进展重试必须一并交付。

### 第四批：真实 Pi 质量与成本验证

先以人工标注的合成／公开多章节样本比较旧大上下文、当前固定小上下文、v2 动态上下文。加入别名、跨章代词、倒叙、梦境、低频关键人物、临时情绪与持久变化、隐藏反证、后文推翻前文、审计未读判断、旧问题被遗漏等样例。

评测重点：主要人物召回、错误 major、发展判断准确性、反证处理、未知校准、问题闭合正确性、两轮隔离、完成率和恢复稳定性。位置与干扰项变化不应使结果大幅漂移。用例多次运行，报告波动；不能仅凭平均值掩盖关键遗漏。

工程指标包括单请求 p50/p95/max、每个有效判断的总输入／缓存／输出、全流程额外审计成本、原文重读比例、补证成功率、无进展调用数和累计耗时。成本下降必须按完整流程计算，不只看角色提交阶段。

先满足预定义语义质量门槛，再比较成本；关键用例不得因节省 token 而退化。没有达标前不扩大到长时间整书 loop。小样本结果也不能声称覆盖所有文学复杂度。
